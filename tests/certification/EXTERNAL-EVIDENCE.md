# External release evidence

Automated local checks do not independently certify a production deployment. `run.py` always reports `production_certified: false`. `evaluate.py` can accept a deployment-specific external evidence bundle only when every required claim is authenticated, current, source-bound, and supported by hashed attachments. No real authority keys or external provider evidence are supplied by this repository.

The operator must provide an independently verified RSA-PSS trust-root public key, a root-signed policy, a signed attestation bundle, attachment directory, and exact release binary. Provision the trust root out of band; generating a key beside a report does not establish independent trust. Signatures authenticate the authorized issuer's statements. They cannot independently prove that a physical laboratory, control-plane audit, or third-party review actually occurred.

Run `python3 tests/certification/evaluate.py --policy POLICY.json --bundle BUNDLE.json --trust-root ROOT.pem --evidence-directory ATTACHMENTS --release-binary RELEASE --output DECISION.json`. A missing, altered, expired, or invalid item produces a false decision and exit status 2. The checked-out source and release binary must match the policy exactly.

The policy and each attestation use `{ "payload": {...}, "signature": "BASE64" }`. Sign the UTF-8 canonical JSON payload (sorted object keys, compact separators, no nonfinite numbers), using SHA-256 and RSA-PSS with digest-length salt. Keys require 3072–8192 bits. Attachments are `{ "path": "relative/path", "sha256": "64 hexadecimal characters" }`; absolute paths, parent traversal, symlinks, duplicate JSON keys and nonregular files are rejected. Verified bytes are captured once before signature verification or JSON parsing.

The executable schema in `evidence.py` and synthetic fixtures in `test_evidence.py` define required fields precisely. Synthetic unit-test keys and reports are temporary test data, never production evidence. A policy binds its ID, source hash, release-binary hash, deployment ID, build organization, validity period, maximum evidence age, required AWS RDS and Vault integrations, performance limits, and issuer organizations/roles/deployments/public-key attachments. Builder and security reviewer must use distinct key identities and organizations. An issuer cannot reuse the root key.

Required signed evidence:

- Release builder: matching automated report with native and Linux checks, strict lint, optimized build, replicated fault checks, PostgreSQL 14–18 compatibility and TLS matrix.
- Independent security reviewer: authentication, TLS, wire protocol, SQL policy, session isolation and provider adapters. High and critical findings require hashed remediation; accepted medium findings require explicit policy approval and a hashed risk acceptance.
- Deployment operator: primary loss, network partition and old-primary rejoin with monotonically advancing epochs, authoritative fencing audits, and at least two independent observer traces. Fence confirmation must precede enabling the replacement writer. Supported authoritative methods are power-off, storage isolation and quorum lease; a PostgreSQL read-only setting alone does not qualify.
- Provider operator: real AWS RDS IAM and Vault authentication, verified backend TLS, lease rotation, rejection of expired leases and fail-closed provider outages, with deployment-specific traces.
- Performance laboratory: physical hardware inventory, virtualization detection, exact deployment identity, at least one hour per workload, declared throughput/latency/sample thresholds, zero errors or dropped samples, and raw measurements for simple selects, prepared selects and rolled-back transactions.

`real_provider.py --authorize-live` is an operator-run acceptance helper. It issues real dynamic credentials and performs read-only probes; it must not be run without an authorized deployment and provider credentials. Vault requires HTTPS and certificate verification; AWS IAM tokens have a 15-minute lifetime ([AWS documentation](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/UsingWithRDS.IAMDBAuth.Connecting.html)). Vault leases follow provider-configured TTLs ([Vault lease documentation](https://developer.hashicorp.com/vault/docs/concepts/lease)). A configured outage-test route is required to observe fail-closed behavior. The helper does not alter external infrastructure to manufacture an outage.

`tests/conformance/failover/observe.py --authorize-live` samples multiple TLS-verified endpoints from a declared vantage point. Its read-only observations do not prove write fencing. An external operator must supply actual authoritative control-plane evidence and write-probe traces. The disposable local power-off fixture exercises a real Docker fence, but certifies no production orchestrator.

Source hashes include tracked and nonignored untracked source/configuration/assets, excluding documentation, deliverables and build artifacts. Passed binary hashes identify files; a remote endpoint's deployed identity requires independently verified operator evidence. Neither provider nor performance helper infers remote deployment identity from a local file hash.

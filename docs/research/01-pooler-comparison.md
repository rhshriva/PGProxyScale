# PostgreSQL Poolers & Wire-Protocol Proxies: Technical Comparison

Open-source / self-hostable only. Stars, versions and dates verified against GitHub and project docs, Sept 2026.

## Limitations & failure modes

1. **PgBouncer is one CPU core per process.** The documented workaround is multiple processes on one port via `so_reuseport` plus `[peers]` for cancel routing — fragmenting one logical pool into per-process pools whose idle counts drift. ([config](https://www.pgbouncer.org/config.html#so_reuseport))
2. **PgBouncer's shared prepared-plan cache breaks on DDL.** Clients with the same query string share one server statement, so `ALTER TABLE` yields `ERROR: cached plan must not change result type`; recovery needs `RECONNECT` on every pooler. ([#1038](https://github.com/pgbouncer/pgbouncer/issues/1038))
3. **PgBouncer's prepared statements need PHP 8.4 *and* libpq 17**; older PHP/PDO must disable server-side prepares. ([FAQ](https://www.pgbouncer.org/faq.html), [#991](https://github.com/pgbouncer/pgbouncer/issues/991))
4. **PgBouncer cannot reuse a SCRAM secret for backend login** unless salt and iterations match exactly, and managed clouds block `pg_authid`, pushing operators toward plaintext. ([config](https://www.pgbouncer.org/config.html#note-on-managed-servers))
5. **PgBouncer stops at pooling**: no internal LB or failover (DNS/HAProxy/`RECONNECT` required), no sharding, admin console simple-protocol-only, and transaction mode loses `SET`/`RESET`, `LISTEN`, `WITH HOLD` cursors, session advisory locks and SQL-level `PREPARE`. ([FAQ](https://www.pgbouncer.org/faq.html), [usage](https://www.pgbouncer.org/usage.html))
6. **PgCat's prepared-statement story contradicts its own README** — advertised as unsupported, implemented behind a default-off cache — and is unreliable in the field (`prepared statement "s21" does not exist`; pgbench prepared protocol `UnexpectedEof`). ([README](https://github.com/postgresml/pgcat), [#734](https://github.com/postgresml/pgcat/issues/734), [#611](https://github.com/postgresml/pgcat/issues/611))
7. **PgCat is incomplete and stalled**: `LISTEN` unimplemented ([#303](https://github.com/postgresml/pgcat/issues/303)), MD5-only client auth with no client certificates, hash-only sharding, connection opening linear and slow ([#616](https://github.com/postgresml/pgcat/issues/616)), no commit since Feb 2025.
8. **Odyssey's prepared-statement reservation is still broken in the field**: `ERROR: prepared statement "2caa56bd" does not exist` with `pool_reserve_prepared_statement` + `pool_smart_discard` under pgjdbc, open since 2022. Its router is "request-reply" and documented as "a potential hot spot", and soft-OOM refuses connections with `FATAL: odyssey: soft out of memory`. ([#477](https://github.com/yandex/odyssey/issues/477), [internals](https://github.com/yandex/odyssey/blob/master/docs/development/internals.md))
9. **pgpool-II has no transaction pooling at all** — only a session-level connection cache — so its client ceiling is `num_init_children` (default 32), with excess clients blocking in the kernel listen queue, and it performs no client↔backend encoding conversion. ([connections](https://www.pgpool.net/docs/latest/en/html/runtime-config-connection.html), [restrictions](https://www.pgpool.net/docs/latest/en/html/restrictions.html))
10. **pgpool-II's parser and proxy state diverge from the backend**: only the first `PREPARE` on a multi-statement line is parsed (`FATAL: unable to bind`), multi-statement queries always go to the primary, SQL type commands are unusable in extended query mode, and `set_config()` reaches only the primary — plus a 2025 report of INSERTs silently vanishing under prepared statements on 4.5.5. ([thread 8893](https://www.pgpool.net/pipermail/pgpool-general/2023-July/008893.html), [thread 9320](https://www.pgpool.net/pipermail/pgpool-general/2025-January/009322.html))
11. **Supavisor's transaction-mode prepared statements are gated behind a default-off flag with no `max_prepared_statements` equivalent**, Supabase's own docs still instruct users to disable prepared statements, and the single-owner-node topology both wastes a relay node and added ~2 ms per query versus co-located PgBouncer (median 4 ms vs 1 ms). ([docs](https://supabase.com/docs/guides/troubleshooting/disabling-prepared-statements-qL8lEL), [blog](https://supabase.com/blog/supavisor-1-million))
12. **pgagroal's transaction pipeline leaks session state by design**: no `DISCARD ALL`, so `SET`, temp tables and cursors persist into the next client, and `idle_timeout`/`max_connection_age` don't reap transaction-mode connections; server-side TLS is documented "Experimental - no pooling" and the fast "performance" pipeline cannot do TLS or failover. ([PIPELINES](https://raw.githubusercontent.com/pgagroal/pgagroal/master/doc/PIPELINES.md))
13. **PgDog still has transaction-mode state-machine bugs**: a `COMMIT` landed on a backend with no open transaction (`pq: unexpected transaction status idle` under golang-migrate), it does not cache anonymous `Parse` (the driver-default case), LISTEN/NOTIFY is off by default and at-most-once, sharded `EXECUTE` broadcasts to all shards, and the license is AGPL-3.0 with features gated to a paid EE. ([#798](https://github.com/pgdogdev/pgdog/issues/798))
14. **pg_doorman is deliberately narrow and has a real memory ceiling**: no statement mode, no LB/sharding, no replication passthrough, no LDAP or client-cert auth, client-facing TLS certs need a restart, `max_memory_usage` excludes prepared-statement bookkeeping (50k+ clients can exceed 1 GB), and the project has just 12 forks. ([pool modes](https://ozontech.github.io/pg_doorman/concepts/pool-modes.html))
15. **ProxySQL's Postgres mode is still second-class** — named portals, `COPY FROM STDIN` in extended mode, `LISTEN`/`NOTIFY` and `Flush` are all unsupported and `Execute(max_rows)` is ignored. ([#4961](https://github.com/sysown/proxysql/issues/4961))

**Cross-cutting gaps for a new entrant:** anonymous/unnamed `Parse` caching is pg_doorman-only; cross-transaction `LISTEN`/`NOTIFY` without pinning is PgDog-only, opt-in and lossy; replication passthrough is missing from PgDog, pg_doorman and pgagroal; sharding-plus-pooling in one binary is PgDog-only and partly experimental; and no pooler routes session advisory locks by lock key — implementations either pin (PgDog, RDS Proxy), reject (pg_doorman) or leak (pgagroal).

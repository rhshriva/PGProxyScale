## 1. Area A — AI/agent-era database workloads

- **Postgres MCP servers in the wild.** [Crystal DBA's Postgres MCP Pro](https://github.com/crystaldba/postgres-mcp) exposes tools (`execute_sql`, `explain_query`, `get_top_queries`, `analyze_workload_indexes`, `analyze_db_health`) and needs `pg_stat_statements`/`hypopg`; the [reference server](https://github.com/modelcontextprotocol/servers-archived/tree/main/src/postgres) exposes schema as MCP *resources* plus read-only queries; also [Supabase](https://github.com/supabase-community/supabase-mcp), [Neon](https://github.com/neondatabase-labs/mcp-server-neon), [Nile](https://github.com/niledatabase/nile-mcp-server), [PG-MCP](https://github.com/stuzero/pg-mcp-server), and [psql-mcp](https://github.com/maxswjeon/psql-mcp) (hardened read-only with credential isolation). Crystal DBA notes both credential patterns leak: MCP client configs rarely store secrets securely, and tool-passed DSNs flow through the LLM into chat history.

- **Agent-access security.** [Tool Poisoning Attacks](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks) hide instructions in tool descriptions (invisible in UI), include "rug pulls" that mutate descriptions after approval, and cross-server shadowing that hijacks trusted tools. [General Analysis demonstrated](https://generalanalysis.com/blog/supabase-mcp-blog) indirect prompt injection via a support ticket driving a `service_role` Supabase MCP server to read `integration_tokens` and copy them into an attacker-visible row — read-only limits writes but not reads the role can already perform. The MCP spec's [security best practices](https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices) name confused-deputy, token passthrough, session hijacking, SSRF, and scope minimization; its [authorization spec](https://modelcontextprotocol.io/specification/2025-03-26/basic/authorization) mandates OAuth 2.1 with [RFC 8414](https://datatracker.ietf.org/doc/html/rfc8414) metadata and [RFC 7591](https://datatracker.ietf.org/doc/html/rfc7591) dynamic registration, audience-bound tokens, and no acceptance of foreign-issued tokens.

- **Text-to-SQL guardrails.** Crystal DBA's restricted mode uses read-only transactions plus a timeout, and parses SQL with [pglast](https://pglast.readthedocs.io/) to reject `COMMIT`/`ROLLBACK` escapes such as `ROLLBACK; DROP TABLE users;`; it warns unsafe procedural languages can circumvent this. [psql-mcp](https://github.com/maxswjeon/psql-mcp) layers `SET default_transaction_read_only = on` + `BEGIN READ ONLY`, rejects psql meta-commands, `COPY … PROGRAM`, `pg_read_file`, `SET SESSION AUTHORIZATION`, `SET … READ WRITE`, and dynamic-SQL executors, and caps output/time. Postgres itself documents [`SET TRANSACTION READ ONLY`/`default_transaction_read_only`](https://www.postgresql.org/docs/current/sql-set-transaction.html) as engine-enforced. Research shows models remain unsafe: [ToxicSQL](https://arxiv.org/abs/2503.05445) plants backdoors so text-to-SQL models emit injectable SQL; [SafeNlidb](https://arxiv.org/abs/2511.06778) argues safety alignment must be added.

- **Vector workloads.** [pgvector](https://github.com/pgvector/pgvector) has two ANN indexes: HNSW gives better speed-recall but slower builds and more memory; IVFFlat builds faster with less memory but weaker queries. HNSW builds are "significantly faster" when the graph fits `maintenance_work_mem`, otherwise the server emits a notice and slows dramatically; builds parallelize via `max_parallel_maintenance_workers`. Builds must be `CREATE INDEX CONCURRENTLY` to avoid blocking writes; unlike B-tree, approximate indexes change query results after creation. Iterative scans can explode work — bounded by `hnsw.max_scan_tuples` (20k default) and `hnsw.scan_mem_multiplier` (multiples of `work_mem`) — making memory/latency spiky and hard to predict; memory estimation exists only as a [proposed PR](https://github.com/pgvector/pgvector/pull/765). Shared ANN indexes let one tenant's vectors degrade another's recall/speed, so pgvector recommends list partitioning for isolation.

- **Agent identity, delegation, rate limits.** OAuth 2.1 + [RFC 8693 token exchange](https://www.rfc-editor.org/rfc/rfc8693.html) is the standard delegation primitive; the IETF [WIMSE credential-delegation draft](https://datatracker.ietf.org/doc/draft-sweeney-wimse-credential-delegation/00/) targets multi-system agent credentials. Per-agent throttling is emerging in gateways ([agentgateway](https://mintlify.wiki/agentgateway/agentgateway/guides/rate-limiting), [MintMCP](https://docs.mintmcp.com/blog/rate-limiting-with-mcp)) — a proxy is the natural broker/enforcer point.

- **Long agent queries vs pools.** Under transaction pooling a long analytical agent query pins one server connection for its duration, so concurrency collapses and clients queue; [pool-exhaustion analyses](https://www.netdata.cloud/guides/pgbouncer/pgbouncer-pool-exhaustion/) show wait times climbing into retry cascades, and PgBouncer's [transaction mode is incompatible with server-side prepared statements](https://www.pgbouncer.org/features.html).

## 2. Area B — Observability / control-plane innovation

- **eBPF reality check.** Socket-level tracing sees only wire bytes; with TLS it sees ciphertext, so query text requires `uprobes` inside the server binary. [eCapture](https://github.com/gojue/ecapture) hooks `exec_simple_query()` via uprobe/uprobe to read plaintext SQL, but needs the `postgres` binary path, root/`CAP_SYS_ADMIN`, symbols (or manual `--offset` when stripped), truncates payloads (~256 B), and adds per-query uprobe latency. [postgres-ebpf](https://github.com/dorkamotorka/postgres-ebpf) is a protocol-observability demo; [pg-lock-tracer](https://github.com/jnidzwetzki/pg-lock-tracer) traces lock behavior. [Coroot's node agent](https://github.com/coroot/coroot-node-agent) and [Pixie](https://github.com/pixie-io/pixie) do L7 tracing at the kernel/agent layer. Kernel view = syscalls, sockets, scheduling, locks; not planner state.

- **Wire-protocol tracing.** [SQLCommenter](https://github.com/google/sqlcommenter) (donated to OpenTelemetry) appends `/*key='value'*/` to SQL to carry trace context, complemented by [OTel database client span conventions](https://opentelemetry.io/docs/specs/semconv/database/database-spans/) (`db.system`, `db.statement`). Driver support is uneven — [npgsql #6255](https://github.com/npgsql/npgsql/issues/6255) tracks OpenTelemetry context propagation into DB traces. Postgres protocol-level labels have been [discussed on pgsql-hackers](https://www.postgresql.org/message-id/C9B3F44D-C90F-4A91-A34B-A09F4FBE58E9%40ardentperf.com) as an alternative to comments.

- **Comment-injection cost.** Injected comments change the SQL string, so prepared-statement/plan caches keyed on text miss (see the [PgBouncer discussion on whether comments are ignored](https://github.com/pgbouncer/pgbouncer/discussions/1044)); every request with a unique trace ID becomes a new parse. [pg_stat_statements](https://www.postgresql.org/docs/current/pgstatstatements.html) derives `queryid` from the post-parse-analysis tree (stable across comments) but stores the first-seen representative `query` text, and its row count is bounded by `pg_stat_statements.max` — comment spam can crowd entries and pollute text.

- **Per-tenant chargeback.** `pg_stat_statements` is the base signal: per `queryid`/`userid`/`dbid` it reports `calls`, `total_exec_time`, `shared_blks_*`, `temp_blks_*`, `wal_bytes` (PG18), enabling cost attribution; [pganalyze](https://pganalyze.com/postgres-analyze-query-performance) productizes this, and [Citus' SaaS design guidance](https://docs.citusdata.com/en/stable/articles/designing_saas.html) covers tenant isolation/sharding. Caveats: text visibility requires `pg_read_all_stats`/superuser, and `queryid` is not stable across major versions or logical replicas.

- **Adaptive concurrency control.** [Netflix concurrency-limits](https://github.com/Netflix/concurrency-limits) applies TCP congestion control to services: Little's Law (`Limit = Avg RPS × Avg Latency`), delay-based Vegas, and Gradient2 for drift/bias, with per-group partition enforcement — directly applicable to per-agent DB quotas. Google SRE's [Handling Overload](https://sre.google/sre-book/handling-overload/) rejects RPS-as-capacity, mandates per-customer CPU quotas, criticality classes (`SHEDDABLE` batch vs `CRITICAL` live), adaptive client-side throttling, bounded retry budgets, and notes connection churn itself is load. For tail latency, [The Tail at Scale](https://dl.acm.org/doi/10.1145/3046682) motivates hedged/tied requests and latency-aware routing.

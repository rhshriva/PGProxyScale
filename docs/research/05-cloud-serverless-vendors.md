## Neon

**Architecture.** Neon splits the database: compute nodes hold no durable state, stream WAL to safekeepers, and commit once a quorum acks via Paxos; the pageserver reconstructs pages at an LSN and persists them to object storage, which is never on the query path ([architecture overview](https://neon.com/docs/introduction/architecture-overview)). This makes branch, restore and replica creation metadata operations (copy-on-write), so branching and scale-to-zero are cheap. Databricks acquired Neon in 2025; Neon docs now describe the same engine as "Lakebase Postgres," running identically on Neon and Databricks ([same page](https://neon.com/docs/introduction/architecture-overview)).

**Proxy.** Neon's proxy is not a SQL pooler: it terminates TLS, authenticates, routes the connection to the correct branch/compute by endpoint, wakes suspended computes, and speaks the WebSocket/HTTP protocol used by the serverless driver. PgBouncer cannot do any of that — it only multiplexes already-established server sessions, cannot wake or provision compute, cannot route by branch, and cannot terminate a WebSocket. Neon separately ships a pooled PgBouncer endpoint for classic clients, so the proxy is the control/routing layer and PgBouncer the optional multiplexer.

**Serverless driver.** WebSockets give one stateful session (transactions, session state, lower latency); HTTP is stateless one-shot/`transaction()`-less query execution with no session state and no prepared statements ([driver docs](https://neon.com/docs/serverless/serverless-driver)). Cold starts come from scale-to-zero compute attach, not the proxy.

## Supabase

Supabase runs one Postgres with two poolers: the shared, multi-tenant **Supavisor** (every project, IPv4-only) and the **dedicated PgBouncer** (paid plans, same machine as Postgres, IPv6 unless the IPv4 add-on). Both read the same pool-size setting but apply it independently, and client and backend limits apply separately to each ([pooling and limits](https://supabase.com/docs/guides/database/connecting-to-postgres/pooling-and-limits)). Guidance: transaction mode for serverless/edge, session mode for IPv4-only networks and BI tools, direct for migrations/dumps/replication ([connect docs](https://supabase.com/docs/guides/database/connecting-to-postgres)).

Documented pain: transaction mode is incompatible with prepared statements, producing `prepared statement "XXX" already exists`; users must set `prepare: false` ([troubleshooting](https://supabase.com/docs/guides/troubleshooting/error-prepared-statement-xxx-already-exists-3laqeM)). Total capacity must satisfy direct + Supavisor backends + PgBouncer backends < Postgres `max_connections`, with headroom for Auth/Storage/PostgREST. The IPv4 add-on is not dual-stack: it swaps the AAAA record for an A record, making the endpoint IPv4-only ([connect docs](https://supabase.com/docs/guides/database/connecting-to-postgres)).

## Prisma Accelerate / Prisma Postgres

Accelerate is a managed global pool plus edge query cache; Prisma ORM routes through it automatically once the connection string is swapped, and `cacheStrategy: { ttl, swr }` serves cached results ([Accelerate](https://www.prisma.io/docs/accelerate)). It therefore constrains application code to Prisma ORM semantics. Documented limits: raw query responses cannot be cached; the fluent API breaks through Client Extensions; heavy or long-running queries are not supported (route them to a replica or separate app) ([known limitations](https://www.prisma.io/docs/accelerate/more/known-limitations)). Pricing is metered and was contentious enough to warrant an official billing FAQ thread ([Prisma discussion #23942](https://github.com/prisma/prisma/discussions/23942)); Prisma Postgres uses Prisma's own pooling and explicitly does **not** support query caching. Critically, Prisma announced Accelerate retires **December 1, 2026**, with migration paths to Prisma Postgres or a direct connection ([Accelerate](https://www.prisma.io/docs/accelerate)).

## Serverless/edge drivers

Neon's driver, Supabase's `prepare:false` + Data API path, Cloudflare Workers `connect()`/Hyperdrive, Vercel, PlanetScale and Drizzle HTTP all solve the same problem: serverless/edge runtimes cannot hold TCP connections, so a proxy terminates an HTTP/WS request and borrows a pooled backend ([Cloudflare](https://developers.cloudflare.com/workers/databases/connecting-to-databases/), [Drizzle edge support](https://deepwiki.com/drizzle-team/drizzle-orm/6.4-serverless-and-edge-runtime-support)). Notably, PlanetScale's Postgres driver is Neon's serverless driver ([PlanetScale docs](https://planetscale.com/docs/postgres/connecting/neon-serverless-driver)). What breaks: interactive transactions over HTTP, prepared statements across borrowed backends, session state (`SET`, temp tables, advisory locks, `LISTEN`/`NOTIFY`), server-side cursors, and predictable latency (extra HTTP hop per query). Drizzle's own guidance is to disable `prepare` behind transaction poolers ([reference](https://github.com/pproenca/dot-skills/blob/master/skills/.experimental/drizzle-nextjs-postgres/references/conn-disable-prepare-behind-transaction-pooler.md)).

## Neon's PolyScale acquisition

PolyScale.ai sold an SQL-aware "global data delivery network" that cached Postgres/MySQL query results in a proxy; Neon published a technical deep dive on its architecture ([Neon blog](https://neon.com/blog/title-a-deep-dive-into-polyscales-architecture)) and had documented connecting Neon to PolyScale ([Neon guide](https://raw.githubusercontent.com/neondatabase/website/0a4bdefef00cfb24a5ac5900fe88866bbbdae7c3/content/docs/guides/polyscale.md)). PolyScale's shutdown notice lived at `polyscale.ai/future`, which now redirects off-domain (to a domain marketplace) — the product is gone, the team/tech absorbed by Neon. **Lesson:** a transparent, correctness-preserving write-through cache in front of Postgres is brutally hard to sell — invalidation must be exact, any stale read is a data-correctness incident, and the database vendor can bundle equivalent routing for free, so the standalone proxy is the layer most easily commoditized and absorbed.

## What these vendors deliberately do NOT solve

- **Cross-database or cross-vendor semantics.** No neutral SQL router, no query rewriting for portability; each layer optimizes for one vendor's engine and one ORM or driver.
- **Cache invalidation correctness.** Caching is opt-in per query (Accelerate `cacheStrategy`), never transparent; nobody guarantees fresh reads for arbitrary SQL.
- **Session-heavy workloads.** Advisory locks, `LISTEN`/`NOTIFY`, cursors, temp tables and `SET` state remain second-class behind transaction pooling and absent over HTTP.
- **Safe multi-tenant pool arithmetic.** They publish the inequality (direct + pooler backends < `max_connections`) rather than solving it; oversubscription still takes down the database.
- **Vendor independence and price control.** Prisma Accelerate's retirement, the PolyScale shutdown and Supabase's IPv4-only shared pooler show the data path is rented, and the rent/roadmap can change under you.
- **Observability into the pool itself.** Diagnosing which pooler, mode, or user exhausted capacity requires reading dashboard reports and `pg_stat_activity`, not the proxy.

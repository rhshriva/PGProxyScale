# Section 3 — Failover & High Availability in the PostgreSQL Proxy Ecosystem

## PgBouncer + Patroni
- PgBouncer's failover primitives are manual and blocking: `PAUSE` disconnects all servers but waits for each server connection to be released per pool mode (in transaction mode the transaction must finish), and new clients to a paused DB block until `RESUME`; `RECONNECT` closes servers only when released; `KILL` drops everything; `WAIT_CLOSE` exists specifically so switchover scripts can confirm a reload/reconnect fully applied ([pgbouncer.org/usage.html](https://www.pgbouncer.org/usage.html)).
- PgBouncer does not drain in-flight transactions around a Patroni failover by itself, so one long transaction stalls `PAUSE`, and a missed `RESUME` freezes the app. GitLab's 2025-07-10 incident: PgBouncer nodes of the `sec` Patroni cluster were left paused after a switchover playbook timed out (waiting on a YubiKey) during Consul CA rotation → ~15 minutes of failing git requests and an SLO violation; re-running the playbook un-paused PgBouncer ([GitLab #20150](https://gitlab.com/gitlab-com/gl-infra/production/-/work_items/20150)).
- "Keeps client connections to a dead primary": client connections stay open, and server connections are only closed/re-resolved when *released* per pool mode, so pooled connections to a dead primary are handed out until the next use fails. PgBouncer ignores errors returned by `server_check_query` and hands out broken connections ([PR #683](https://github.com/pgbouncer/pgbouncer/pull/683)); multi-host lists explicitly have "no mechanisms to skip unreachable hosts" ([config docs](https://www.pgbouncer.org/config.html)); if no server is available, queries queue instead of failing fast unless `query_wait_timeout` is set ([#585](https://github.com/pgbouncer/pgbouncer/issues/585)). [#1311](https://github.com/pgbouncer/pgbouncer/issues/1311) documents post-switchover breakage; [#715](https://github.com/pgbouncer/pgbouncer/issues/715) shows a concurrent `RESUME` can make `PAUSE` hang permanently.
- Since 1.23, `SIGTERM` = `SHUTDOWN WAIT_FOR_CLIENTS` (zero-drop rolling restart) and `SIGQUIT` = immediate shutdown ([usage.html](https://www.pgbouncer.org/usage.html), [#1361](https://github.com/pgbouncer/pgbouncer/issues/1361)). CVE-2025-2291 (security-policy bypass, all versions <1.24.1) was fixed in PgBouncer 1.24.1 ([CERT-FR](https://www.cert.ssi.gouv.fr/avis/CERTFR-2025-AVI-0339/), [PostgreSQL announcement](https://www.postgresql.org/about/news/pgbouncer-1241-released-fixes-cve-2025-2291-3059/)).
- Patroni's own Citus integration pauses client connections on the coordinator during worker switchovers (measured ~2.9 s latency spike, zero client errors) — the coordination PgBouncer users must script themselves ([Citus blog](https://www.citusdata.com/blog/2023/03/06/patroni-3-0-and-citus-scalable-ha-postgres/)).

## VIPs, DNS and Consul
- vip-manager binds a VIP from the Patroni `/leader` key in etcd/Consul or the REST `/leader` endpoint (`trigger-key=/service/<scope>/leader`, `trigger-value=<member>`, 1000 ms default poll); it needs root/CAP_NET to add the address (or the Hetzner API), and Postgres needs `listen_addresses=*` or `net.ipv4.ip_nonlocal_bind=1` ([vip-manager README](https://github.com/cybertec-postgresql/vip-manager)).
- pgpool-II's watchdog manages the VIP natively via `if_up_cmd`/`if_down_cmd`/`arping_cmd`, with the same root/sudo caveat ([pgpool watchdog intro](https://www.pgpool.net/docs/pgpool-II-4.5.6/en/html/tutorial-watchdog-intro.html)). keepalived/VRRP is not quorum-based: a partitioned pair can both hold MASTER, and it moves the IP, not Postgres — there is no fencing ([keepalived split-brain](https://stackoverflow.com/questions/75686533)).
- DNS failover is the sum of independent delays. Route 53 health checks need >18% of checkers to agree, use a 30 s standard interval and a 1–10 failure threshold (≥90 s detection at 30 s×3); one measured drill: ~95 s detect + ~3 s propagation + 10 s–minutes resolver cache + 10–60 s client cache = ~2–4 min user-visible despite a "60 s TTL". If all records are unhealthy, Route 53 still returns the *primary* record ([Route 53 pitfalls](https://hidekazu-konishi.com/entry/route_53_health_check_failover_pitfalls.html)).
- Aurora's DNS zone TTL is 5 s and AWS warns that client TTLs >5 s keep sending writes to the blue writer after switchover ([AWS blue/green switching](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/blue-green-deployments-switching.html)); RDS Multi-AZ rewrites the DNS record and forces reconnects, "typically 60–120 seconds", with a recommended JVM TTL ≤60 s ([AWS Multi-AZ failover](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZ.Failover.html)).
- Consul: DNS queries default to `stale` consistency — typically within 50 ms of the leader but with **no upper bound** — and a no-quorum cluster can still answer stale reads, so a partitioned follower can advertise a stale "primary" ([Consul consistency modes](https://developer.hashicorp.com/consul/api-docs/features/consistency)).

## pg_auto_failover
- Architecture: a central **monitor** (a Postgres instance + extension) is authoritative; keepers report via `pgautofailover.node_active()` and the monitor health-checks nodes and drives the FSM; a 3-node setup survives losing any one node. Monitor failure does not break replication but stops all failover reaction ([architecture docs](https://pg-auto-failover.readthedocs.io/en/main/architecture.html)). Replication is synchronous by default; when the standby is unhealthy the primary enters `wait_primary` and sets `synchronous_standby_names=''` (writes continue, failover effectively disabled). With async (`synchronous_commit=local`) failover is not initiated if the standby is >10 WAL segments behind, and during manual failover the old primary keeps accepting writes until the standby is caught up, the primary dies, or 2 minutes pass ([architecture docs](https://pg-auto-failover.readthedocs.io/en/main/architecture.html)).
- Maintenance: the repo now lives under the **hapostgres** org (redirect from citusdata), 1,390 stars, 106 open issues, last push 2026-09-07, not archived ([GitHub](https://github.com/hapostgres/pg_auto_failover)). Issue [#867](https://github.com/hapostgres/pg_auto_failover/issues/867) ("Make PG-Auto-Failover high-availability") is open; [#1178](https://github.com/hapostgres/pg_auto_failover/issues/1178) documents a monitor `PGconn` leak that accumulated 189 orphaned backends against `max_connections=200`; [#1063](https://github.com/hapostgres/pg_auto_failover/issues/1063) (open since Jan 2025) has `DROP DATABASE` hanging and flooding deadlocks, with fix [PR #1108](https://github.com/hapostgres/pg_auto_failover/pull/1108) still unmerged; [#1089](https://github.com/hapostgres/pg_auto_failover/issues/1089) leaves secondaries "down" after switchover when cert names differ.
- vs Patroni: one monitor node instead of a quorum DCS, no etcd/Consul/ZooKeeper, and no watchdog/STONITH layer — partition handling is its own keeper/monitor protocol, not consensus.

## ProxySQL (PostgreSQL + MySQL)
- ProxySQL's PG model separates detect/decide/promote/rewire: ProxySQL does **not** promote, heal, preserve in-flight transactions, or prevent data loss ("a transaction open on the old primary … is gone"). Rewiring is explicit admin SQL or implicit via `pgsql_replication_hostgroups` + `check_type='read_only'`, bounded by `monitor_read_only_interval` (default 1500 ms); `OFFLINE_SOFT` drains, `OFFLINE_HARD` drops immediately ([ProxySQL failover primer](https://proxysql.com/blog/proxysql-postgresql-failover-primer/)).
- Measured: unplanned primary SIGKILL → median 1900 ms (1500–2100 ms) to resume writes, zero errors across 1.76 M transactions; planned `OFFLINE_SOFT` switchover → median 1100 ms with only ~200 ms of actual disruption; Patroni+ProxySQL kept the app alive over a 10,000 ms window with zero errors while the Patroni+HAProxy baseline saw pgbench die on the connection cut ([ProxySQL failover primer](https://proxysql.com/blog/proxysql-postgresql-failover-primer/)).
- MySQL: Group Replication membership changes are surfaced by ProxySQL's monitor via `mysql_group_replication_hostgroups` (hostgroup moves are automatic), but choosing/promoting the new primary is GR's job or an operator's; async/topology failover requires an external decision engine such as Orchestrator ([ProxySQL GR configuration](https://www.proxysql.com/documentation/group-replication-configuration)).

## PgDog
- PgDog polls every configured backend for LSN, `pg_is_in_recovery()` and last-transaction timestamp; when enabled it auto-detects replica promotion and redirects writes, and can ban lagging replicas from read traffic ("replica lag ban"). The same docs page has a dedicated **Split brain** section alongside failover and logical replication ([PgDog replication & failover](https://docs.pgdog.dev/features/load-balancer/replication-failover/); I could not extract the split-brain subsection text — the page renders truncated — so treat its exact wording as unverified). Dynamic role discovery was still an open request in [#563](https://github.com/pgdogdev/pgdog/issues/563), i.e. roles were historically configured explicitly.

## Split-brain: Patroni DCS, watchdog, quorum, async data loss
- Patroni requires a consensus DCS with compare-and-set and TTLs: etcd (Raft), Consul (Raft), ZooKeeper (Zab), or the Kubernetes API (backed by etcd). The primary holds a TTL'd `/leader` key; if the key update fails, Postgres is demoted *before* the lock expires because from one node a DCS outage is indistinguishable from a partition ([Citus blog](https://www.citusdata.com/blog/2023/03/06/patroni-3-0-and-citus-scalable-ha-postgres/), [DCS failsafe mode](https://patroni.readthedocs.io/en/latest/dcs_failsafe_mode.html)).
- Async mode explicitly permits losing committed transactions: worst case ≈ `maximum_lag_on_failover` bytes of WAL **plus** everything written in the last `ttl` seconds (≈`loop_wait`/2 on average); lost commits sit on an unrecoverable forked timeline ([replication modes](https://patroni.readthedocs.io/en/latest/replication_modes.html)).
- `synchronous_mode: on` refuses to promote a standby unless it holds every transaction that returned a successful commit; if no suitable standby exists, the primary still accepts writes and **no standby is promoted** when it fails (availability loss, not silent data loss). `synchronous_mode_strict` blocks writes instead. Even so, transactions can be lost if a backend is cancelled while awaiting replication ack; and clients using `synchronous_commit=off|local` can lose data ([replication modes](https://patroni.readthedocs.io/en/latest/replication_modes.html)).
- Watchdog: Patroni arms `/dev/watchdog` to expire ~5 s before the TTL. With defaults `loop_wait=10`, `ttl=30`, the HA loop has ≥15 s (`ttl − safety_margin − loop_wait`) before reset; a 10 s DCS timeout leaves only ~5 s to terminate clients. `safety_margin=-1` (expire at `ttl//2`) is the only absolute guarantee ([watchdog support](https://patroni.readthedocs.io/en/latest/watchdog.html)).
- `failsafe_mode`: when the leader lock update fails for reasons other than a value/index mismatch, the primary may keep running only if it can reach **all** known members over the REST `/failsafe` API; if one member does not answer, it demotes. Quorum is deliberately not used, because a majority of Patroni nodes can end up on the losing side of a partition ([DCS failsafe mode](https://patroni.readthedocs.io/en/latest/dcs_failsafe_mode.html)).

## Planned switchover with zero dropped transactions
- `patronictl switchover` targets healthy clusters and demotes the leader first; `patronictl failover` is for unhealthy clusters, may promote an async node, and the docs warn it "can cause data loss depending on how up-to-date the promoted replica is" ([patronictl](https://patroni.readthedocs.io/en/latest/patronictl.html)).
- Patroni maintains a `/sync` key with strict ordering invariants so a node that is not leader/current sync standby cannot self-promote; in `synchronous_mode=quorum` it publishes `synchronous_standby_names='ANY n (…)'` plus a `quorum` count, guaranteeing any quorum-sized subset includes a node with the latest commit ([replication modes](https://patroni.readthedocs.io/en/latest/replication_modes.html)).
- The "last transaction" gap: `synchronous_commit=on`/`remote_write` guarantees the standby *received/flushed* WAL, not that it replayed it, so a promoted standby can be missing the final commit from the client's view; `remote_apply` waits until standby queries can see the commit and is the strongest setting ([PostgreSQL `synchronous_commit`](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT)).
- AWS blue/green is the closest managed analogue: guardrails (replication health, replica lag, no active writes on green, no long-running DDL/unsupported DDL on blue), stop new writes, **drop connections in both environments**, wait for green to catch up, then rename instances/endpoints; timeout 30–3,600 s, default 300 s, with automatic rollback on timeout. With RDS Proxy, blue goes read-only before green is promoted while the proxy still routes to blue, so apps can see `AdminShutdown: terminating connection due to administrator command`, and existing proxy connections are dropped when green is promoted ([AWS blue/green switching](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/blue-green-deployments-switching.html)).

## Citus
- Patroni 3.0+ manages a Citus fleet with one `scope` and `citus: {group: 0 for coordinator, 1..N for workers}`; it creates/populates `pg_dist_node` and keeps it updated on coordinator/worker failover or switchover, and pauses client connections on the coordinator primary during controlled worker switchovers so clients see no error (observed ~2.9 s latency spike) ([Citus blog](https://www.citusdata.com/blog/2023/03/06/patroni-3-0-and-citus-scalable-ha-postgres/)).
- Citus itself has no built-in coordinator HA: the coordinator holds only a few MB of metadata, so the documented options are a streaming-replication hot standby (promoted manually or by an external controller) or restoring metadata from backup; a second coordinator can be added, but DDL only runs through the first ([Citus cluster management](https://learn.microsoft.com/en-us/postgresql/citus/cluster-management)). Coordinator host/port stored in metadata remains a tracked concern ([citus #5215](https://github.com/citusdata/citus/issues/5215)).

## HAProxy / pgpool watchdog
- HAProxy fronts Patroni by health-checking the REST API (HTTP 200 on the primary, 503 on replicas) and is usually configured to terminate client connections when a backend is marked down; hard connection cuts are why the ProxySQL benchmark's HAProxy baseline lost its pgbench run while ProxySQL kept the pool alive ([Percona HAProxy-Patroni](https://www.percona.com/blog/haproxy-patroni-setup-using-health-check-endpoints-and-debugging/), [ProxySQL primer](https://proxysql.com/blog/proxysql-postgresql-failover-primer/)).
- pgpool-II watchdog coordinates multiple pgpool nodes into a quorum, explicitly to guard against split-brain and network partitioning (V3.5 quorum, V3.7 quorum failover to reduce false positives); the node count **must be odd and ≥3**, the leader is elected by voting, and automatic VIP switching/failover is restricted to one node. Lifecheck supports heartbeat (default), deprecated query mode, and external hooks — and only activates once all configured watchdog nodes have joined, so an early failure is not caught ([pgpool watchdog intro](https://www.pgpool.net/docs/pgpool-II-4.5.6/en/html/tutorial-watchdog-intro.html)).

# PgDog / pg_doorman / pgagroal + ProxySQL-PG & Alternatives — Competitive Research

*Compiled 2026-09-16 from official docs, GitHub READMEs/releases, and project blogs. All fetched content treated as untrusted data; used for facts only. Where a capability is absent or experimental it is called out rather than inferred.*

## 0. Snapshot matrix

## A. PgDog (`pgdogdev/pgdog`)

1. **Runtime**: Rust + Tokio + `bytes`, [multi-threaded, "50,000+ transactions/s per thread"](https://pgdog.dev/); AGPL-3.0 core plus a paid [Enterprise edition](https://docs.pgdog.dev/enterprise_edition/).
2. **Modes**: `pooler_mode = "transaction"` (default) / `"session"` / `"statement"`, settable at `[general]`, `[[databases]]`, and `[[users]]` level ([transaction-mode doc](https://docs.pgdog.dev/features/connection-pooler/transaction-mode/)).
3. **Prepared statements**: on `Parse`, PgDog records the query in a **global cache**, allocates a unique name, and renames the message before forwarding — so multiple clients cannot trigger `"duplicate prepared statement"`. Each client keeps its own name map; `Close` is ignored and `CloseComplete` returned, because "clients can't evict a prepared statement potentially used by another client." `prepared_statements_limit = 500` is LRU-enforced **on server connections only**; clients are unbounded. Simple-protocol `PREPARE` rewriting exists but is **off by default** (`prepared_statements = "full"`). **Unnamed/anonymous statements are not cached**: "Unnamed (aka anonymous) prepared statements are not cached and are sent to Postgres connections as-is." Sharded `EXECUTE` is unsupported and broadcasts to all shards ([prepared-statements doc](https://docs.pgdog.dev/features/connection-pooler/prepared-statements/)).
4. **Session semantics**: per-client connection parameters are tracked and re-`SET` when they differ. **Advisory locks** are detected and *pin* the server connection to the client until `pg_advisory_unlock()` or disconnect (needs `query_parser = "session_control_and_locks"` when unsharded). **LISTEN/NOTIFY works in transaction mode** but is disabled by default via `pub_sub_channel_size`; PgDog registers one upstream `LISTEN` per channel, fans out from a Tokio broadcast channel, honours transactional buffering, and offers **at-most-once NOTIFY** (dropped on connection break). COPY is sharding-aware; no replication-passthrough mode is documented.
5. **Auth**: SCRAM-SHA-256 / MD5 / plain, plus `server_auth = "rds_iam"` (AWS RDS IAM), `azure_workload_identity`, `vault_dynamic`, `vault_static`. No LDAP/OAuth/PAM/cert-auth documented.
6. **TLS**: client + server TLS, self-signed or CA, and per-database TLS incl. mTLS since v0.1.58 ([TLS doc](https://docs.pgdog.dev/features/tls/)).
7. **Routing/HA**: round-robin, random, least-active; health checks; read/write split via the native parser (`pg_raw_parse`); failover by replication monitoring with `role = "auto"` and `lsn_check_delay` ([README](https://github.com/pgdogdev/pgdog)).
8. **Observability**: PgBouncer-style admin DB (`SHOW CLIENTS/SERVERS/POOLS/CONFIG/STATS/PREPARED/REPLICATION`, `RELOAD`, `FORCE_RELOAD`, `RECONNECT`, `PAUSE`, `RESUME`, `MAINTENANCE`), OpenMetrics and OTEL ([admin doc](https://docs.pgdog.dev/administration/)). The admin DB "doesn't support prepared statements or transactions" ([metrics doc](https://docs.pgdog.dev/features/metrics/)).
9. **Hot reload**: `RELOAD` is async; `FORCE_RELOAD` (new in v0.1.58) guarantees new pools for all subsequent transactions.
10. **Multi-tenancy**: physical (sharding) and virtual (schema/row) ([multitenancy doc](https://docs.pgdog.dev/features/multi-tenancy/)).
11. **Scale**: 2M+ qps in production, 20 TB+ sharded, 1.4M Docker pulls; three-person team ([funding post, 2026-06-10](https://pgdog.dev/blog/our-funding-announcement/)).
12. **Health**: created 2024-12-27; 282 forks, 193 open issues; **weekly releases on Thursdays**. Docs warn that "some [sharding features] are still experimental and are marked accordingly."

## B. pg_doorman (`ozontech/pg_doorman`)

1. **Runtime**: Rust, MIT, multi-threaded with a **single shared pool across all worker threads**; three years in production at Ozon ([docs home](https://ozontech.github.io/pg_doorman/)).
2. **Modes**: `pool_mode: "transaction"` (default) or `"session"`, with per-user override. **Explicitly no statement mode** ([pool-modes](https://ozontech.github.io/pg_doorman/concepts/pool-modes.html)).
3. **Prepared statements — its differentiator**: every anonymous `Parse` is hashed (query text + param OIDs + planner-GUC digest) and remapped to an internal `DOORMAN_<N>` name; on a server-cache hit pg_doorman **synthesises `ParseComplete`** and skips the round-trip. Three cache layers: pool `prepared_statements_cache_size` (default 8192, approximate LRU), client-named (unbounded `AHashMap`), client-anonymous `client_anonymous_prepared_cache_size`, and per-backend `server_prepared_statements_cache_size` (true LRU, issues `Close`). `prepared_statements: false` disables; `prepared_statements_cache_size: 0` is **rejected**. Documented caveats: PG's custom/generic plan decision is shared across clients; async pipeline mode gets unique `DOORMAN_async_<N>` so the server cache cannot be reused; worst-case backend plan memory `8192 × ~100 KB ≈ 800 MB`; stale anonymous state yields `ERROR: unnamed prepared statement does not exist` (SQLSTATE `26000`) ([prepared-statements doc](https://ozontech.github.io/pg_doorman/tutorials/prepared-statements.html)).
4. **Session semantics**: `SET`/`RESET` outside a transaction, advisory locks held across transactions, and `WITH HOLD` cursors **do not work** in transaction mode (`SET LOCAL` does). Cleanup is mutation-tracked (`RESET ALL` / `DEALLOCATE ALL` / `CLOSE ALL`), opt-out via `cleanup_server_connections: false`. LISTEN/NOTIFY works **only inside a transaction**. **Replication passthrough is not supported** ([comparison](https://ozontech.github.io/pg_doorman/comparison.html)).
5. **Auth**: MD5, SCRAM-SHA-256 passthrough (extracts `ClientKey`), `auth_query` (dedicated + passthrough), PAM, `pg_hba.conf`, JWT(RSA-SHA256), Talos. **No LDAP, no cert auth, no SCRAM channel binding** ([auth overview](https://ozontech.github.io/pg_doorman/authentication/overview.html)).
6. **TLS**: client 4 modes; server-to-PG 5 modes incl. mTLS; server certs hot-reload on `SIGHUP`, **client-facing certs require restart**.
7. **HA**: Patroni-assisted fallback via REST `GET /cluster` (`patroni_api_urls`, `fallback_cooldown`), plus a bundled `patroni_proxy` with role routing and `max_lag_in_bytes`. **No sharding.**
8. **Observability**: built-in Prometheus `/metrics` with HDR-histogram p50/p90/p95/p99, JSON logs, admin psql DB (`SHOW POOLS`, `SHOW POOLS_MEMORY`, `SHOW PREPARED_STATEMENTS`, `SHOW INTERNER`, `SHOW POOL_COORDINATOR`, `SHOW POOL_SCALING`), and an embedded SPA on the same port (`[web].ui = true`, silently demoted if `general.admin_password` is empty/`"admin"`) with oauth2-proxy/Keycloak SSO ([web UI](https://ozontech.github.io/pg_doorman/guides/web-ui.html)).
9. **Hot reload**: `SIGHUP` for pools/users/hba/server TLS; `SIGUSR2` binary upgrade with session migration via `SCM_RIGHTS` (TLS migration only in a `tls-migration` build, absent from distro packages and Docker) ([signals](https://ozontech.github.io/pg_doorman/operations/signals.html)).
10. **Multi-tenancy**: per-pool isolation; Talos routes `clientId` → pool.
11. **Memory ceilings**: `max_memory_usage` caps in-flight buffers but **not** prepared-statement bookkeeping; 10k clients × 256 entries × ~80 B ≈ 200 MB, while 50k+ clients can cross 1 GB. Pool Coordinator adds `max_db_connections`, `reserve_pool_size`, `min_guaranteed_pool_size`, `min_connection_lifetime` (30 s default) with p95-ranked eviction ([pool settings](https://ozontech.github.io/pg_doorman/reference/pool.html)).
12. **Health**: created 2025-03-05; 12 forks, only 8 open issues; release cadence much slower than PgDog.

## C. pgagroal (Red Hat lineage)

1. **Runtime**: C17, process model + shared memory, `liburing` for network I/O, atomics for state ([README](https://github.com/pgagroal/pgagroal)); BSD-3-Clause.
2. **Modes are "pipelines"**: `pipeline = auto|performance|session|transaction`. `auto` picks **performance** unless `tls`, `failover`, or `disconnect_client` are set, in which case it silently downgrades to **session**.
3. **Prepared statements**: `PREPARE`/`DEALLOCATE` are **unsupported in the transaction pipeline**; with `track_prepared_statements = on` (default `off`) pgagroal issues `DEALLOCATE ALL` before returning a connection. No protocol-level reprepare or name remapping ([pipelines doc](https://pgagroal.github.io/doc/PIPELINES.html), [config](https://pgagroal.github.io/doc/CONFIGURATION.html)).
4. **Session semantics in transaction pipeline**: `SET`/`RESET`, `LISTEN`/`NOTIFY`, `WITH HOLD CURSOR` unsupported; **no `DISCARD ALL` on return**, so temp tables/cursors/GUCs leak between clients; `idle_timeout` and `max_connection_age` do not reap transaction-mode connections; `disconnect_client` and `allow_unknown_users` unsupported; `blocking_timeout` applies and is advised to be `0`.
5. **Auth**: `pgagroal_hba.conf` (`trust`/`reject`/`password`/`md5`/`scram-sha-256`), `auth_query`, user vault, split frontend users. No LDAP/IAM/OAuth/PAM surfaced.
6. **TLS**: TLS 1.2+ for clients, metrics and remote management; **server-side TLS is documented as "Experimental - no pooling"**.
7. **HA**: `failover = on` + `failover_script` to trigger external failover; `health_check` (2.1.0); database aliases; up to 64 server sections.
8. **Observability**: Prometheus endpoint, Grafana 12 dashboard, simple web console (new in 2.1.0), `pgagroal-cli` remote management.
9. **Hot reload**: config reload supported and hardened in 2.1.0 (fixes for [#729](https://github.com/pgagroal/pgagroal/pull/729) reload crash, [#731](https://github.com/pgagroal/pgagroal/pull/731) `log_file` not cleared); several TLS keys still "Changes require restart".
10. **Multi-tenancy**: per-database/per-user limits via `pgagroal_databases.conf` (DATABASE USER MAX_SIZE INITIAL_SIZE MIN_SIZE).
11. **Ceilings**: `max_connections` default **100**, hard max **10 000**; 64 HBA entries, 64 limit entries.
12. **Health**: created 2019-08-28; 121 forks, 75 open issues. Top contributor is `jesper.pedersen@redhat.com` (401 commits) — the Red Hat lineage is real, but the project now presents itself as "The pgagroal community" with **mnemosyne systems** as sponsor, not Red Hat.

## D. Other self-hostable / notable options

- **ProxySQL 3.x PostgreSQL mode**: extended-query protocol supported **since 3.0.3**, auto-enabled; queues `Parse`/`Bind`/`Describe` and routes on `Sync`, with a prepared-statement cache. Unsupported: **named portals, `COPY FROM STDIN` in extended mode, `LISTEN`/`NOTIFY`, the `Flush` message**; `Execute(max_rows)` ignored; query cache disabled; session-level `SET` not rolled back on error. Named portals are "planned for a future release" ([doc](https://www.proxysql.com/documentation/postgresql-extended-query-protocol)).
- **Heimdall Data**: **closed-source commercial** proxy/console. Multiplexing **pins** on transaction start, prepared statement, or temp-table creation; per-tenant connection limits ([doc](https://www.heimdalldata.com/advanced-connection-pooling-for-azure/)).
- **KubeDB**: not a pooler itself — an operator that manages **PgBouncer** and **Pgpool** CRDs (Pgpool `4.4.5`, `4.5.0`) plus ProxySQL ([docs](https://kubedb.com/docs/v2025.1.9/guides/pgpool/)).
- **Neon**: pooled endpoint is **PgBouncer in transaction mode** (`max_client_conn=10000`, per-user/db pools at 90% of `max_connections`); SQL-level `PREPARE`/`DEALLOCATE`, `SET`, `LISTEN`/`NOTIFY`, `WITH HOLD CURSOR`, and session advisory locks are **unsupported**, though protocol-level prepared statements are ([Neon docs](https://neon.com/docs/connect/connection-pooling)). Neon also ships its own **Rust** proxy (auth/routing, SQL-over-HTTP, Postgres-over-WebSocket; `--auth-backend=console|postgres|web`) ([proxy README](https://github.com/neondatabase/neon/blob/main/proxy/README.md)).
- **Crunchy Bridge pooler**: managed **PgBouncer** on port `5431`, activated by `CREATE EXTENSION crunchy_pooler`; transaction mode default, `max_prepared_statements` default **250**; session and statement modes available; superuser/replication roles denied. **Self-hostable only as vanilla PgBouncer**, not as a Crunchy product ([doc](https://docs.crunchybridge.com/how-to/pgbouncer)).
- **Amazon RDS Proxy**: **not self-hostable**. Transaction-level multiplexing with *pinning*; PostgreSQL-specific gaps: **no session pinning filters, `SET` always pins, any statement >16 KB pins, no `CancelRequest` support, no streaming replication, protocol 3.0 only, no direct SSL negotiation**; auth via IAM + Secrets Manager; 20 proxies/account ([limits](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-proxy.html), [pinning](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-proxy-pinning.html)).
- **pgproxy (`taufik-rama/pgproxy`)**: Go, Redis-backed **read-cache** proxy, not a pooler; author states it is "still an experimental tooling" that mainly works for read-only queries ([README](https://github.com/taufik-rama/pgproxy)).
- **pg_shardman**: the original `postgrespro/pg_shardman` URL now **404s**; the surviving source is [`kotsachin/pg_shardman`](https://github.com/kotsachin/pg_shardman), last pushed **2017-11-09** — effectively **abandoned**. It is a PostgreSQL *extension* (partitioning + `postgres_fdw` + logical replication), **not a wire-protocol proxy**, so it is not comparable.
- **Alibaba PolarDB-X / PolarDB**: PolarDB-X is a **MySQL-protocol** distributed database; it is not a self-hostable Postgres wire proxy. No Postgres-wire pooling component with verifiable public evidence was found — treat as out of scope rather than "missing a feature".

## E. Implications for a next-gen pooler

The defensible gaps are visible in the matrix: (a) **anonymous/unnamed `Parse` caching** is unique to pg_doorman — PgDog explicitly does not cache unnamed statements, and neither does pgagroal nor ProxySQL; (b) **LISTEN/NOTIFY in transaction mode without pinning** is only solved by PgDog (with at-most-once NOTIFY and an off-by-default channel); (c) **statement mode** is offered by PgDog and ProxySQL but rejected by pg_doorman and available-but-lossy in pgagroal; (d) **replication passthrough** is absent from PgDog, pg_doorman and pgagroal (PgBouncer 1.23+ has it); (e) **sharding + pooling in one binary** is PgDog-only among the OSS set, but partially experimental; (f) every product's transaction mode still breaks *some* subset of `SET`, advisory locks, and `WITH HOLD` cursors — the only divergence is whether it *pins* (PgDog), *rejects* (pg_doorman), *silently leaks* (pgagroal), or *pins invisibly* (RDS Proxy).

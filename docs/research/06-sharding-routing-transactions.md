# PostgreSQL Proxies Beyond Connection Pooling: Sharding, Scaling, Routing, HA

## 1. Sharding middleware

**Citus is an extension, not a proxy.** It runs *inside* PostgreSQL: a coordinator holds metadata in `pg_dist_*` and pushes fragments to workers ([concepts](https://docs.citusdata.com/en/stable/get_started/concepts.html)). Citus 12 added **schema-based sharding** — `citus_schema_distribute('tenant')` pins a whole schema to a colocation group, so tenants need no shard key ([DDL reference](https://docs.citusdata.com/en/stable/develop/reference_ddl.html)); Citus 14.1/13.3 lets schema DDL run from any node ([release notes](https://www.citusdata.com/updates/v14-1/)). But cross-schema **foreign keys and joins are unsupported** ([limitations](https://docs.citusdata.com/en/stable/develop/reference_workarounds.html)).

**The coordinator is the structural bottleneck.** Citus concedes that "in some write-heavy use cases… the coordinator becomes a performance bottleneck"; its remedy is a second coordinator, but **DDL only runs through the first**, and coordinator failover is manual — replicate metadata or restore ([cluster management](https://learn.microsoft.com/en-us/postgresql/citus/cluster-management)). Teams cite coordinator saturation as the main reason they abandon Citus ([tinybird review](https://www.tinybird.co/blog/citus-reviews)).

**Rebalancing** uses logical replication, is non-blocking since 11.0 (the only write lock is subscriber-shard metadata promotion), requires a replica identity, and in 13.2 gained snapshot-based node addition. Cumulatively it revealed that **disk snapshots could be inconsistent**: because commits are 2PC, a snapshot may capture a transaction committed on some nodes and merely *prepared* on others — the fix was new `citus_cluster_changes_block()/_unblock()` UDFs ([release notes](https://www.citusdata.com/updates/v14-1/)).

**PgCat** is a Rust pooler whose README marks sharding **Experimental**: `SET SHARD TO '1'`, `SET SHARDING KEY TO '1234'`, comment hints, and `sqlparser`-based auto-detection. It uses `PARTITION BY HASH`, so every query must carry the shard key; [issue #771](https://github.com/postgresml/pgcat/issues/771) shows a filterless `SELECT` silently not fanning out. There is no cross-shard engine ([README](https://github.com/postgresml/pgcat)).

**PgDog** is the most ambitious OSS proxy: parser-extracted shard keys, list/range/hash maps in `pgdog.toml`, per-row `COPY` sharding, in-memory cross-shard SELECT with MIN/MAX/SUM/COUNT, and `SET pgdog.shard` manual routing ([sharding](https://docs.pgdog.dev/features/sharding/), [list/range](https://pgdog.dev/blog/list-and-range-sharding)). It admits a real cross-shard query engine is still being built.

**ProxySQL has no PostgreSQL sharding at all** — its sharding guide is entirely MySQL (`mysql_users`, `mysql_query_rules`) and states that "cross-shard joins must be handled at the application level… ProxySQL routes to a single hostgroup per query" ([sharding guide](https://proxysql.com/documentation/how-to-setup-proxysql-sharding/)). **Pgpool-II** is a pooler/HA controller with coarse statement-level balancing and no distributed planner. **SharDingSphere-Proxy** supports Postgres but is SQL-rewrite middleware with a long compatibility tail (e.g. [#37533](https://github.com/apache/shardingsphere/issues/37533)). **Vitess** remains the MySQL-only reference point — VTGate, vschema, VReplication resharding; PgDog describes itself as "somewhat similar in architecture to Vitess" ([docs](https://docs.pgdog.dev/features/sharding/)).

**Production reality.** Notion **rejected Citus and Vitess** because "the actual clustering logic is opaque" and hand-rolled sharding: **480 logical shards on 32 physical databases** (15 per host, to divide evenly at 40/48), dual-write + audit-log migration, three days to copy on a 96-CPU box, minutes of downtime ([Notion](https://www.notion.com/blog/sharding-postgres-at-notion), [summary](https://www.besthub.dev/articles/how-notion-scaled-postgresql-with-database-sharding-067807eb1f31)). Shopify sharded in 2015, then had to build "pods" because `with_each_shard` meant one bad shard broke the whole platform ([Shopify](https://shopify.engineering/a-pods-architecture-to-allow-shopify-to-scale)). Uber's Postgres→MySQL move cited replication/MVCC limits ([Uber](https://www.uber.com/us/en/blog/postgres-to-mysql-migration/)).

**NewSQL alternatives.** Spock/pgEdge is logical multi-master *replication*, not sharding — explicit conflict resolution, no global transaction manager ([Spock conflicts](https://github.com/pgEdge/spock/blob/main/docs/conflicts.md)). YugabyteDB (YSQL over Raft) and CockroachDB give PG wire compatibility plus consensus, at a Raft latency floor and a stream of caveats ([Yugabyte advisories](https://docs.yugabyte.com/stable/releases/techadvisories/ta-30772/), [CRDB vs PG](https://appmaster.io/blog/postgresql-vs-cockroachdb-multi-region)). They **replace** Postgres; a proxy **keeps** it.

## 2. Read/write splitting

The decision procedure is crude: parse, look for `SELECT`, check transaction state, route. PgCat sends SELECTs to replicas and everything else — "including explicit transactions" — to the primary, with `SET SERVER ROLE TO 'primary'|'replica'|'auto'` escape hatches ([README](https://github.com/postgresml/pgcat)). ProxySQL warns blanket `^SELECT` rules "**do not use in production**" (they break transactions, session state, consistency) and prescribes hand-curated digest rules ([R/W split](https://proxysql.com/documentation/proxysql-read-write-split-howto/)). Its Postgres path adds `pgsql_replication_hostgroups`, monitor-driven `pg_is_in_recovery()` role detection and per-replica `max_replication_lag` soft exclusion ([failover primer](https://proxysql.com/blog/proxysql-postgresql-failover-primer/)).

Lag sampling is stale by design (`monitor_read_only_interval` defaults to **1500 ms**). Read-your-writes is the unsolved part: the trick is session pinning after a write, or tagging the session with the write LSN and reading only replicas that replayed past it. HeliosProxy documents exactly that (`max_replica_lag_ms = 100`) ([Helios](https://www.heliosdb.com/docs/proxy/tutorials/lag-aware-routing/)), and PostgreSQL 19 adds a server-side `WAIT FOR` LSN primitive proxies could delegate to ([devblogs.sh](https://devblogs.sh/posts/read-your-writes-wait-for-in-postgresql-19)). No mainstream proxy implements RYW.

## 3. Failover and HA

ProxySQL's framing — **detect, decide, promote, rewire** — is the clearest: a proxy owns only 1 (partly) and 4. Its docs are blunt: ProxySQL "does not preserve in-flight transactions… A write committed on the old primary but not yet replicated is lost. That defense lives at the PostgreSQL layer." Measured single-host: SIGKILL + `pg_ctl promote` → **median 1900 ms window (1500–2100 ms), zero pgbench errors across 1.76 M transactions**; planned switchover with `OFFLINE_SOFT` drain → **median 1100 ms, ~200 ms of real error gap**; Patroni+ProxySQL → **10,000 ms** but zero app errors, whereas Patroni+HAProxy **killed pgbench on the connection cut** ([primer](https://proxysql.com/blog/proxysql-postgresql-failover-primer/)).

Patroni is the de facto authority (etcd/Consul/ZK quorum, watchdog fencing, `synchronous_mode`/`remote_apply`); pg_auto_failover is lighter, with a monitor node. Bare PgBouncer keeps clients pointed at the dead primary — hence VIPs or `PAUSE`/`RESUME` orchestration ([Stack Harbor](https://stackharbor.com/en/knowledge-base/cluster-pgbouncer-failover-routing/)). PgDog polls LSN/`pg_is_in_recovery()`, bans lagging replicas, re-routes writes, and documents its split-brain caveat ([PgDog failover](https://docs.pgdog.dev/features/load-balancer/replication-failover/)). Citus coordinator failover stays manual.

## 4. Query routing intelligence

Routing today is regex/digest matching, statement-class heuristics and transaction state — nothing plan-aware. ProxySQL's own workflow is: send everything to the primary, read `stats_mysql_query_digest`, then hand-write rules ([docs](https://proxysql.com/documentation/proxysql-read-write-split-howto/)). PgCat's plugin system is still [RFC #437](https://github.com/postgresml/pgcat/issues/437); PgDog has plugins plus an enterprise QoS/plans tier. Pgpool-II's `statement_level_load_balance` has documented bugs, e.g. ignoring `load_balance_mode` ([pgpool-hackers, Feb 2024](https://pgpool.net/pipermail/pgpool-hackers/2024-February/004427.html)). Nothing does cost-based or learned routing.

## 5. Distributed transactions and correctness

PostgreSQL's own docs say `PREPARE TRANSACTION` is "not intended for use in applications or interactive sessions": a prepared transaction holds its locks, blocks VACUUM, can force shutdown against XID wraparound, and without an external transaction manager you should keep `max_prepared_transactions = 0` ([docs](https://www.postgresql.org/docs/current/sql-prepare-transaction.html)). A 2026 pgsql-hackers report shows a failed `COMMIT PREPARED` leaving locks in `pg_locks` invisible to `pg_prepared_xacts`, releasable only by restarting the server ([thread](https://www.postgresql.org/message-id/CAJDiXggXjXhzdYg4KNyrn%3Dtq6iWESG79te%2BRsGJhaq9pzxqCyg%40mail.gmail.com)). PgBouncer lists `PREPARE`/session features as **"Never"** under transaction pooling ([features](https://www.pgbouncer.org/features.html)).

Citus doubled down on 2PC: `citus.multi_shard_commit_protocol` defaults to `2pc`, and the 1PC alternative was deleted — "All multi-shard modifications are done via 2PC" ([commit e483ea7](https://github.com/citusdata/citus/commit/e483ea7efe8d51c77b26d3a754df8c3f82cc7eac)) — though the GUC lingers in the docs ([docs bug](https://github.com/citusdata/citus_docs/issues/1071)). It requires `max_prepared_transactions` raised "typically to the same value as max_connections" on every worker, and COPY-under-2PC opens a connection per shard, so M concurrent copies × N shards yields `could not connect to any active placements` ([GUC](https://docs.citusdata.com/en/stable/develop/api_guc.html), [errors](https://learn.microsoft.com/en-us/postgresql/citus/common-errors?view=citus-13)). Worst case, [#6548](https://github.com/citusdata/citus/issues/6548): on a multi-database cluster 2PC recovery "gets stuck, blocking the new transactions," worked around by stopping the coordinator and manually `ROLLBACK PREPARED`-ing over dblink. Distributed deadlock detection aborts victims with `canceling the transaction since it was involved in a distributed deadlock`, and ordering bugs persist ([#7477](https://github.com/citusdata/citus/issues/7477)).

PgDog's 2PC is honest but limited: "eventually consistent cross-shard writes… a very high chance of being atomic," not a guarantee ([2PC](https://docs.pgdog.dev/features/sharding/2pc/)). Crash recovery is experimental — "If PgDog were to crash during this step, it would be impossible to determine the state of each transaction on each shard" ([crash recovery](https://docs.pgdog.dev/features/sharding/2pc/crash-recovery/)) — and partial cross-shard errors can go undetected ([#454](https://github.com/pgdogdev/pgdog/issues/454)).

Cross-shard correctness is structurally constrained: unique/PK constraints must include the distribution column; FKs across distributed schemas are unsupported; `FOR UPDATE`, recursive CTEs, `GROUPING SETS`, `TABLESAMPLE` and outer joins are single-shard or distribution-column-only; Citus sequences "don't work for sequences smaller than BIGINT" ([limitations](https://docs.citusdata.com/en/stable/develop/reference_workarounds.html)). Citus has shipped wrong ORDER BY/LIMIT pushdown results ([#2027](https://github.com/citusdata/citus/issues/2027), [#2021](https://github.com/citusdata/citus/issues/2021)); PgDog's scatter/gather only recognises `=`/`IN` key predicates ([docs](https://docs.pgdog.dev/features/sharding/cross-shard-queries/select/)).

Theory says don't wait for a fix: FLP rules out fully asynchronous consensus under one unannounced failure ([Lynch et al.](https://groups.csail.mit.edu/tds/papers/Lynch/jacm85.pdf)), and 2PC is inherently blocking — the coordinator's failure leaves participants uncertain, which is why Paxos Commit needs 2F+1 coordinators ([Gray & Lamport](http://research.microsoft.com/pubs/64636/tr-2003-96.pdf)). Exactly-once delivery is impossible at the network layer; production fakes it with idempotency ([Treat](https://bravenewgeek.com/you-cannot-have-exactly-once-delivery/)). Hence the default is **sagas with hand-written compensations and lost isolation** ([saga](https://microservices.io/patterns/data/saga.html)) plus transactional outbox ([outbox](https://microservices.io/patterns/data/transactional-outbox.html)).

## 6. Multi-tenant isolation via proxy

Three models. **Schema-per-tenant via proxy** (PgDog sharded schemas, Citus schema-based sharding) maps schema→shard: cheap isolation, no tenant column. **Database-per-tenant** isolates hardest but explodes connections and catalogs (PgCat's dynamic-database gap is [#923](https://github.com/postgresml/pgcat/issues/923)). **Shared tables + tenant column** gives density but needs `SET LOCAL`/`SET app.tenant_id` plus RLS enforced *in the DB* — a proxy that rewrites queries but forgets RLS is a cross-tenant leak. Noisy neighbours are inherent when tenants share shards; Citus's answer is `isolate_tenant_to_new_shard()` + `citus_move_shard_placement` for Zipfian big tenants ([cluster management](https://learn.microsoft.com/en-us/postgresql/citus/cluster-management)). Per-tenant rate limiting barely exists OSS: PgBouncer's per-user limits are connection-count only ([#678](https://github.com/pgbouncer/pgbouncer/issues/678)); per-tenant CPU/IO QoS is an enterprise feature (PgDog QoS). Transaction pooling also leaks session state — `server_reset_query` is the only guardrail, and a missed reset is a tenant-data-leak bug class.

## Top 10 unsolved problems in Postgres scaling that a proxy could attack

1. **Plan-aware routing** — route by estimated cost/shape, not `^SELECT`.
2. **Read-your-writes as a primitive** — LSN-tagged sessions, PostgreSQL 19 `WAIT FOR` support.
3. **Zero-dropped-transaction switchover** — drain in-flight work, then cut over with no client-visible error (ProxySQL's best case still leaks ~200 ms).
4. **Cross-shard atomicity without `max_prepared_transactions`** — proxy-side saga/outbox with idempotent commit and crash-recoverable state.
5. **Online resharding with no maintenance window** — built-in dual-write, backfill, cutover: the thing every large team hand-builds.
6. **Connection-state safety under transaction pooling** — detect/repair leaked `SET`, temp tables, advisory locks, prepared statements.
7. **A real cross-shard query engine** — ORDER BY/LIMIT/aggregate/join pushdown without buffering the world in proxy memory.
8. **Per-tenant QoS** — quotas, admission control, priority, and noisy-neighbour isolation at the proxy.
9. **Control-plane HA** — proxy metadata that survives without Citus's single-writer coordinator.
10. **Failover correctness for in-flight work** — deterministic retry semantics, split-brain fencing, and a defensible answer to "was my committed write lost?"

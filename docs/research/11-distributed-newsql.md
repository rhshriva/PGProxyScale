# Section 1 research — Distributed/NewSQL databases vs sharding middleware

## Vitess (MySQL sharding proxy) and the missing Postgres equivalent
- Vitess horizontally shards and operates MySQL/Percona only; VTGate advertises itself as MySQL 8.4, and Postgres appears only as an *import source* for migrating into Vitess/MySQL ([supported DBs](https://vitess.io/docs/24.0/overview/supported-databases/), [PlanetScale import](https://planetscale.com/docs/vitess/imports/postgres)).
- Components: VTGate (proxy accepting MySQL protocol and routing to shards), VTTablet (agent beside each MySQL), and a Topology Service on etcd/ZooKeeper/Consul holding a consistent cluster view ([what is Vitess](https://vitess.io/docs/24.0/overview/whatisvitess/)).
- VSchema declares keyspaces, sharded vs unsharded, vindexes per table and sequence tables, and drives query routing and resharding ([VSchema](https://vitess.io/docs/24.0/concepts/vschema/)).
- VReplication streams MySQL **binlog** events near-real-time, powering MoveTables (vertical sharding/migration), Reshard (shard split/merge), Materialize, Online DDL, VDiff consistency checks and VStream CDC; the workflow is create → copy/replicate → switchtraffic → complete, with reverse replication for rollback and read-traffic-before-write-traffic cutover ([VReplication reference](https://raw.githubusercontent.com/planetscale/database-skills/main/skills/vitess/references/vreplication.md)).
- Pooling/protection: multiplexes thousands of app connections onto a small MySQL pool, plus query de-duping, transaction management, query rewriting and query killing ([what is Vitess](https://vitess.io/docs/24.0/overview/whatisvitess/)).
- There was never a Vitess-for-Postgres because routing and data movement are tied to MySQL's binlog/GTID and dialect. That gap is now being filled by **Multigres** (Supabase, by Vitess co-creator Sugu Sougoumarane): "an adaptation of Vitess for Postgres" with MultiGateway + MultiPooler, a Materializer that mirrors VReplication, Postgres 2PC for cross-shard transactions, and Multiorch consensus HA ([Multigres docs](https://multigres.com/docs), [CMU talk](https://db.cs.cmu.edu/events/pg-vs-world-multigres-sugu-sougoumarane/)); and by **PlanetScale Neki** (Aug 2025), "sharded Postgres by the team behind Vitess" that is explicitly "not a fork of Vitess", with shards/shard groups/shard indexes, reference tables and a replicator ([Neki](https://planetscale.com/blog/announcing-neki), [data topology](https://planetscale.com/docs/neki/data-topology)).

## Spock / pgEdge — logical multi-master replication
- Spock provides multi-master logical replication for Postgres 15–19 (needs a patched Postgres build and `track_commit_timestamp`); every node holds a full copy, all nodes accept writes, shared-nothing, **no coordinator** ([spock README](https://github.com/pgEdge/spock), [pgEdge blog](https://www.pgedge.com/blog/unleashing-the-power-of-postgresql-with-pgedge-distributed-multi-master-replication-and-postgres-platform-part-1)).
- It is not sharding: writes commit locally and replicate asynchronously, so there are **no global/cross-node transactions**; RPO is "seconds" for async edge nodes, and synchronous logical replication doubles commit latency (2× inter-region RTT) ([pgEdge architecture models](https://docs.pgedge.com/platform/prerequisites/architecture/)).
- Conflicts: default `last_update_wins`, delta-apply columns for counters (`local + (new − old)`), INSERT conflicts auto-converted to UPDATE, and unresolvable conflicts logged to `spock.exception_log`/`spock.resolutions` so replication keeps running ([conflicts](https://raw.githubusercontent.com/pgEdge/spock/main/docs/conflicts.md)).
- Limitations: UPDATE/DELETE require a PK/replica identity; only one unique index can drive conflict resolution; deferrable uniques are skipped; **foreign keys are not enforced during replication**; there is no replication-queue flush, so schema changes must be made with writes stopped on all nodes; some DDL is not replicated; sequences need pgEdge Snowflake ([limitations](https://raw.githubusercontent.com/pgEdge/spock/main/docs/limitations.md)).
- Spock 6 moved progress tracking out of the catalog into shared memory + a custom WAL RMGR, added spill-to-disk replay queues, per-subscription conflict stats, and ACE table-diff/repair to detect and fix silent drift after node loss ([Spock 6](https://www.pgedge.com/blog/spock-6-the-only-logical-choice)).

## YugabyteDB
- YSQL is "built by reusing the PostgreSQL language layer code", wire-compatible on port 5433; the base is PG11 before v2.25 and PG15 in v2025.1/v2.25+. YCQL is the Cassandra-rooted semi-relational API on 9042 (independent APIs; per-table opt-in transactions, DML only) ([query layer](https://docs.yugabyte.com/stable/architecture/query-layer/), [API](https://docs.yugabyte.com/stable/api/)).
- Storage: DocDB (customized RocksDB LSM, one instance per tablet); tables are hash-sharded by default (or range-sharded) into tablets, each a Raft group across YB-TServers, with writes acking after RF/2+1; YB-Master holds metadata ([DocDB](https://docs.yugabyte.com/stable/architecture/docdb/), [Raft](https://docs.yugabyte.com/stable/architecture/docdb-replication/raft/)).
- Overhead: multi-node transactions and JOINs "experience inter-node latency, making queries slower than in single-node databases like PostgreSQL"; connection setup is ~13–18.5 ms vs ~2.4–2.9 ms for Postgres (both ~0.5–1.4 ms behind PgBouncer), because catalog misses RPC the master leader ([FAQ](https://docs.yugabyte.com/stable/faq/general/), [connection latency](https://dev.to/yugabyte/postgres-and-yugabyte-connection-latency-35ch)).
- Issue #10108 documented ~300× slower inserts than Postgres; Yugabyte's 2025 update reports ~16K/s after tuning ([issue](https://github.com/yugabyte/yugabyte-db/issues/10108#issuecomment-2788127862)). Unsupported: exclusion/deferrable constraints, GiST, XML, XA, UNLOGGED tables and several index types; Read Committed can raise "Restart read required" from clock skew ([compat](https://docs.yugabyte.com/stable/reference/configuration/postgresql-compatibility/), [read restart](https://docs.yugabyte.com/stable/architecture/transactions/read-restart-error/)).
- Benchmarks: TPC-C scales 25,646 → 51,297 tpmC from 3 → 6 nodes at ~99.7% efficiency, New Order latency 54–62 ms ([horizontal scaling](https://docs.yugabyte.com/stable/benchmark/tpcc/horizontal-scaling/)).

## CockroachDB
- pgwire "protocol v3.0" and "majority of PostgreSQL syntax", reporting `server_version` PG18; libpq and rust-postgres are only Partial. Unsupported: range types, events, DROP PRIMARY KEY, XML functions, column-level privileges, XA, foreign data wrappers, session-scoped advisory locks; `SERIAL` is non-monotonic `unique_rowid()`, integer division returns decimal, triggers are row-level only, PostGIS is a subset ([compat](https://docs.cockroachlabs.com/docs/stable/postgresql-compatibility)).
- Latency floor: official "single-row reads in 1 ms … single-row writes in 2 ms within a single availability zone". Parallel commits get a distributed commit down to one consensus round, but intent resolution still needs two, so contention hurts; cross-region write latency equals the RTT to the closest quorum replica (NoVA↔Oregon ≈37 ms theoretical, 60–80 ms practical) ([performance](https://raw.githubusercontent.com/cockroachdb/docs/main/src/current/v25.1/performance.md), [tradeoffs](https://www.cockroachlabs.com/blog/fundamental-tradeoffs-distributed-databases/)).
- Gateway: every node is symmetric and any node acts as the client "SQL gateway" (parse/plan, TxnCoordSender/DistSender to leaseholders). A protocol-aware pgwire proxy that migrates live sessions (RFC #47060) was never shipped; Cloud uses `sqlproxyccl` plus a 10-minute session-revival token ([design](https://raw.githubusercontent.com/cockroachdb/cockroach/master/docs/design.md), [session revival RFC](https://raw.githubusercontent.com/cockroachdb/cockroach/master/docs/RFCS/20211203_session_revival_token.md)).
- Benchmarks: TPC-C 140k warehouses / 81 nodes = 1,684,437 tpmC at 95.45% efficiency, p50 newOrder 402.7 ms; a 3-node 2,500-warehouse run = 31,065 tpmC, p50 88.1 ms. Independent pgbench TPC-B on one host: Postgres 2.53 ms/395 tps vs CockroachDB 1-node 6.28 ms/159 tps and 3-node 10.49 ms/95 tps ([TPC-C large](https://raw.githubusercontent.com/cockroachdb/docs/main/src/current/v25.1/performance-benchmarking-with-tpcc-large.md), [pgbench](https://github.com/philippta/postgresql-cockroachdb-benchmark)).

## Tibero / other Postgres-compatible systems
- Tibero (TmaxSoft) is a Korean commercial, Oracle-compatible RDBMS whose HA is shared-disk active-active clustering (TAC + Tibero Active Storage), not sharding or NewSQL; it is relevant mainly as an Oracle migration target ([TAC/TAS](https://tmaxtibero.blog/high-availability-dbms-tibero-tac-tas/)). Tmax's Postgres-based **OpenSQL** bundles PostgreSQL + Patroni + etcd + a Rust connection pooler (OpenProxy) + Barman — HA/pooling, not distributed SQL ([OpenSQL overview](https://docs.tibero.com/tmaxopensql.en/overview.md)).

## Citus vs YugabyteDB vs CockroachDB positioning
- Citus is a Postgres *extension*: coordinator + workers, distributed tables sharded by a distribution column, co-location, reference tables, and an adaptive executor that pushes a whole query into one shard when the distribution column is filtered — preserving 100% Postgres/extension compatibility (PostGIS, JSONB, UDFs). It targets single-region multi-tenant SaaS, real-time analytics and time series ([Citus README](https://raw.githubusercontent.com/citusdata/citus/main/README.md)).
- Where each breaks: Citus wins single-region throughput and Postgres fidelity, but the coordinator is the metadata/DDL entry point (schema changes and admin must go through it), cross-shard transactions use 2PC, there is no automatic globally-consistent multi-region story, and OSS HA relies on Patroni. YugabyteDB and CockroachDB give Raft-based multi-region consistency and automatic failover, but pay a consensus latency floor, have real PG feature/extension gaps, and are slower on small/contended single-region workloads.
- Benchmark positioning is contested: GigaOM's HammerDB TPROC-C test (sponsored by Microsoft) put Azure Cosmos DB for PostgreSQL/Citus ahead of CockroachDB Dedicated and Yugabyte Managed at 1,000 warehouses, which Yugabyte disputed on methodology ([InfoQ](https://www.infoq.com/news/2023/07/distributed-postgresql-benchmark/), [Microsoft](https://devblogs.microsoft.com/cosmosdb/distributed-postgresql-benchmarks-using-hammerdb-by-gigaom/)).
